# Idea — 阶段 11：本地音频转写为 Note

> **状态：设计已确认，待实施。** 阶段 10 提供固定北京地域的阿里云 Keychain 凭证；本阶段在阶段 9 的 Files 与 Notes 基础上增加语音转写能力。
>
> 核心目标：**一段 MP3，变成一篇可阅读、可编辑、随时精确回听的普通 Markdown Note。**

## 为什么要做

用户经常需要将多人会议录音整理为可检索、可编辑的逐字稿，尤其关注中文技术术语、说话人、句子级毫秒时间戳，以及随时返回原始音频核对。人工在普通转写文本和音频进度之间反复寻找位置很费力。

啪嗒无需发展为会议管理应用：转写只是**创建 Note 的另一种方式**。记录仍是普通 Note，MP3 仍是普通文件资源。

## 只需一条主流程

1. 在 Notes 的新建操作中选择「从音频创建笔记」，导入本地 MP3。
2. Pata 将原始 MP3 **复制**到 Vault 的 `files/`，不修改或移动外部原件；必要时只为上传生成临时单声道副本。
3. 使用阶段 10 的北京地域 API Key，通过阿里云百炼 `qwen-audio-3.1-asr-flash-filetrans` 异步识别，并启用说话人区分。
4. 将识别结果转为普通 Markdown Note；保留句子级 `HH:MM:SS.mmm` 时间戳、说话人和原始文件引用。
5. Note 顶部是极简音频播放器：点击正文时间戳跳转原音频；拖动播放器并松开后，正文自动定位并轻微高亮对应句子。
6. 用户可正常编辑 Note。播放器 `···` →「重新转写」使用原始 MP3 再次识别；成功后确认是否替换原有逐字稿，失败不影响旧稿。

## 本阶段交付

- **一个 Note**：继续使用现有 Markdown Note 数据模型、单列列表与全区域编辑器；无 `Transcript` 顶层实体。
- **一个原始 MP3**：复用阶段 9 `files/` 与标准 Markdown 文件引用；不做特殊文件管理页面。
- **一个播放器**：顶部播放/暂停、进度条、当前时间/总时长；其他交互按需利用系统能力，不做音频编辑器。
- **两个定位方向**：正文时间戳 → 播放器；播放器拖动结束 → 正文。自然播放不强制逐字稿跟随滚动。
- **一个重新转写入口**：直接使用唯一配置模型；不让用户挑模型或供应商。
- **可靠的失败保护**：上传或转写失败显示可重试提示；重新转写不静默覆盖人工编辑。

## 非目标

不做实时录音/转写、内置 AI 摘要、翻译、会议纪要、参会人管理、说话人身份库、字幕导出、音频剪辑、时间轴工作台、进度条持续强制滚动、JSON 侧车、数据库、云同步、OSS 配置、多 ASR 供应商框架及超长会议自动切换服务。
