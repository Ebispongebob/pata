# File Safety — 本地数据完整性

## 保存步骤（推荐）

1. 读取当前文件内容及 hash/mtime，建立 UI 编辑基线。
2. 提交时重新检测磁盘版本；如和基线不同且本地有未保存修改，**停止覆盖并提示**。
3. 写入同目录临时文件，flush 后原子替换（须验证目标文件系统行为）。
4. 修改后更新索引，使用内部写入标识/内容 hash 防止 fsnotify 重复反馈。
5. 故障时保留原文件和恢复路径，不只保留内存草稿。

## 外部编辑

- `fsnotify` 仅作为变化通知，监听可能丢事件、编辑器可能以 rename 代替 write；应有扫描/恢复机制。
- 外部 Pi Agent 可编辑内容，但可能写出非法 Frontmatter；App 不应自动清空不可解析文件，而应隔离错误并报告路径与原因。
- **不要同步监听事件直接触发不受保护的回写**。

## 分层责任

- Markdown 源文件是业务真相。
- 内存缓存、搜索索引、页面状态可丢弃重建。
- DayPlan 是真实数据，虽然在隐藏目录内也必须备份。
- 仅保存正文的编辑操作不能破坏未知 YAML 字段。

## 验收场景

双编辑窗口、外部编辑同时保存、文件临时删除再重命名、无效 YAML、UTF-8 中文/emoji、断电模拟、目录重命名、失效 ID 引用。
